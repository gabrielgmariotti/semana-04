Semana 1 — HTML: o esqueleto de toda página

HTML (HyperText Markup Language) não é linguagem de programação — é linguagem de marcação. Ela não calcula nem decide nada; só diz ao navegador O QUE cada pedaço de conteúdo é: título, parágrafo, imagem. Toda página da internet, do Google à Kinho, começa com esse esqueleto.

Tag

O que faz / onde usar

Se faltar, o que acontece

<!DOCTYPE html>

Avisa o navegador: "HTML moderno". Primeira linha de todo arquivo, sempre, uma vez só.

A página abre, mas em "modo antigo" (quirks mode): o navegador imita os anos 90 e o layout pode sair torto.

<html lang="pt-BR">

Abre o documento e declara o idioma. Uma vez, envolvendo tudo.

Funciona, mas leitor de tela pronuncia errado, o Chrome oferece tradução errada e o Google entende pior a página.

<head>

Os bastidores: informações SOBRE a página que não aparecem nela. Uma vez, antes do body.

O navegador improvisa um invisível. Funciona "no susto", mas o código vira bagunça de amador.

<meta charset="UTF-8">

Permite acento e ç. Primeira linha dentro do head.

O clássico: "Calçados" vira "CalÃ§ados".

<title>

Nome na abinha do navegador e título do link no Google. Dentro do head, um por página.

A aba mostra o nome do arquivo e você fica feio na busca.

<body>

O palco: tudo aqui dentro aparece na tela. Uma vez, todo o conteúdo visível.

O navegador improvisa, igual ao head. Funciona, mas é desleixo.

<h1> ... </h1>

Título principal (heading 1). UM por página — é o assunto dela. <h2> a <h6> = subtítulos.

Texto grudado, sem hierarquia. O Google não sabe o assunto; leitor de tela não acha nada.

<p> ... </p>

Parágrafo. Um para cada bloco de texto.

Mesmo problema: texto vira um bloco só.

<label>

Etiqueta de um campo: o texto que diz ao humano o que digitar ali.

Campo sem nome — usuário no escuro.

<input type="number" id="...">

Caixa onde o usuário digita. type="number" só aceita número. Tag solteira, sem fechamento.

Sem type, aceita qualquer coisa; sem id, o JavaScript não encontra o campo.

<button>

O botão. Ganha vida com onclick.

Sem onclick, clica e nada acontece — decorativo.

</tag> (fechamento)

Toda tag que abre, fecha. A barra "/" é o fechar.

O navegador CHUTA onde fecha. Às vezes a página INTEIRA vira título gigante.

A lição mais importante da semana

HTML não tem mensagem de erro. O navegador é um funcionário que nunca reclama: recebe instrução errada, dá de ombros e improvisa. O erro fica invisível até aparecer como acento quebrado ou layout torto. A disciplina vem de você. (JavaScript é o oposto: erra e ele grita — no Console.)

Exercício que vale ouro: quebrar de propósito. Apaga o charset, salva, recarrega (Cmd+R) e olha os acentos. Depois desfaz (Cmd+Z). Erro que você VIU não se esquece.

Semana 1 — Git, GitHub e Vercel: o caminho até o ar

Página no teu Mac = file:// — só tua máquina vê. Site de verdade = https:// — um servidor que nunca desliga serve o arquivo pra qualquer pessoa. Três estações no caminho: Git (máquina do tempo local), GitHub (álbum na nuvem) e Vercel (o computador que serve a página ao mundo).

O ciclo sagrado (decorar — é assim até a semana 13)

EDITA → SALVA (Cmd+S) → COMMIT (foto com legenda) → SYNC (empurra pro GitHub) → o Vercel percebe e ATUALIZA O SITE SOZINHO. Mudança que não apareceu? Percorre de trás pra frente: sincronizou? commitou? salvou?

O que é

Detalhe de quem usa

Foto do código num momento, com legenda.

Tem assinatura (user.name/email) e código único (hash, ex.: d77f164).

push / Sync

Empurrar os commits do Mac pro GitHub.

No VS Code o botão chama "Sync Changes".

branch main

A linha principal do histórico.

Push na main = deploy de produção automático no Vercel.

repository

A "pasta" do projeto no GitHub, com histórico.

Regra do portfólio: 1 projeto = 1 repositório público = 1 link.

deploy / build

Publicar: o Vercel busca, prepara e espalha o código.

"Building..." → "Ready" = no ar. 404 = não existe deploy ali.

Os 3 chefões da madrugada (bugs reais que você derrotou)

  • Assinatura vazia: Mac novo sem user.name/user.email — o Git se recusa a commitar. Correção: git config --global, uma vez. Bônus: e-mail noreply do GitHub esconde teu e-mail pessoal dos commits públicos.
  • Nome não é identidade: o projeto do Vercel ficou preso ao repositório VELHO (deletado) mesmo o novo tendo o MESMO nome. Mesma família do Index.html vs index.html: teu Mac perdoa maiúscula, o servidor Linux não.
  • Cache: a internet guarda cópias temporárias — às vezes você vê a versão velha por uns minutos. Não é bug teu.
  • A moral: toda mensagem de erro diz a causa. Ler COM CALMA é metade do debug.

Semana 2 — Teu primeiro JavaScript (a calculadora)

HTML descreve; JavaScript EXECUTA. O triângulo de toda interface: EVENTO (clique) → chama FUNÇÃO → função executa INSTRUÇÕES.

Peça

O que faz

Detalhe que salva

<script>

A ilha de JavaScript dentro do HTML.

Vai antes do </body>.

function nome() {}

Receita com nome: só roda quando alguém chama.

Nome começa minúsculo (calcular). Parênteses = a "boca" (vazia por ora); chaves = o corpo.

onclick="calcular()"

O fio: liga o clique à função.

Os parênteses são o ato de chamar.

const caixa = ...

Cria variável: caixinha com nome.

À esquerda do = nasce a caixinha NOVA; à direita só entram as que JÁ existem. Nome repetido = erro.

document.getElementById("id")

Pega o elemento pelo id (o "CPF" da tag).

Sem id, o JS fica cego.

.value

LÊ o que o usuário digitou.

Vem SEMPRE como texto.

Number(...)

Converte texto em número.

Sem isso, "50"+"10" gruda em "5010".

.textContent = ...

ESCREVE texto dentro de um elemento.

O contrário do .value.

.toFixed(2)

Arredonda pra 2 casas decimais.

Dinheiro se mostra assim: 4000.00.

alert("...")

Janelinha com mensagem.

Perfeita pra testar se um botão está vivo.

O Console — a caixa-preta do navegador

JavaScript grita os erros no Console (Chrome: Cmd+Option+J). Anatomia: "Uncaught ReferenceError: calcular is not defined (index.html:19:34)" = tipo do erro + tradução ("chamaram um nome que não existe") + endereço arquivo:linha:coluna. As linhas "at ..." empilhadas são o stack trace — o caminho do crime, lido de baixo pra cima. Atenção: a linha apontada é onde EXPLODIU — o culpado pode morar em outra.

Lições que custaram bug (12/07)

  • Maiúscula importa: calcular() e Calcular() são duas pessoas diferentes.
  • Singular vs plural: parcelas (quantidade) e parcela (valor de cada uma) são DUAS caixinhas.
  • Corrigiu uma coisa, atropelou outra: mexeu perto, confere o vizinho.

Semana 2, parte 2 — if, validação e juros (25/07)

O último pilar entrou em campo: estruturas de controle. Código que DECIDE: "SE a entrada for inválida, avisa e para." Calculadora de balcão aguenta cliente digitando qualquer coisa.

Peça

Tradução / o que faz

Detalhe que salva

if (condição) { }

if = se. SE a condição for verdade, executa o bloco; senão, pula ele.

Vive no corpo da função, DEPOIS das leituras — não dá pra conferir caixinha antes de enchê-la.

<= e >=

Menor-ou-igual / maior-ou-igual.

parcelas <= 0 pega zero E campo vazio (Number("") vira 0). Um if, dois bugs mortos.

return

return = retornar: encerra a função ALI.

O segurança da porta: entrada inválida não passa pra conta.

* (asterisco)

Multiplicar.

juros / 100 transforma "2" em 0,02 — porcentagem virando número.

Juros simples

total = restante + restante × taxa × meses.

Com juros 0 a fórmula devolve o valor puro — à vista funciona sem if extra.

As leis das chaves (pagas com suor em 25/07)

  • Cada { abre uma porta; cada } fecha a porta MAIS RECENTE ainda aberta. Quem abre primeiro fecha por último: função abre → if abre → if fecha → função fecha.
  • Dois ifs são IRMÃOS (um fecha antes do outro abrir), não pai e filho. If dentro de if depois de um return = código morto: nunca executa.
  • ✗ 0 no rodapé = gramática válida, NÃO = código certo. Chave errada compila e faz a coisa errada (a função fechou cedo e o cálculo ficou "na rua").
  • Ferramenta: clica ao lado de uma { e o VS Code acende a } parceira. Raio-X do encanamento.
  • Esteira de debug: erro no console → conserta → recarrega → próximo erro. Um de cada vez, sem pânico.
  • Teste de fronteira: o >= se testa com o caso IGUAL (entrada 100 numa compra de 100), não só com o maior. Instinto de QA.

Raio-X: linhas dissecadas átomo por átomo

As linhas mais importantes dos teus 3 projetos, abertas peça por peça: o que cada pedaço é, por que precisa estar ali, e o que acontece se faltar. Os átomos se repetem em TODO código que existe — dissecando estas 5 linhas, você leu todas.

Primeiro, o alfabeto invisível: a pontuação

Símbolo

Nome e função

Se usar errado

( )

Parênteses: entregam ingredientes a uma função — Number(texto), alert("oi") — ou agrupam uma condição: if (x > 2). Vazios = "sem ingredientes": buscar().

Faltou fechar = erro de sintaxe na hora. Coisa no lugar errado dentro deles = o bug da function calcular(if...).

{ }

Chaves: delimitam um BLOCO (corpo de função, corpo de if). Cada { abre uma porta; cada } fecha a mais recente aberta.

Chave a mais fecha a função cedo demais (o cálculo ficou "na rua"); a menos, o bloco engole o resto do arquivo.

" "

Aspas: TEXTO LITERAL. "50" é texto; 50 é número. "resultado" entre aspas = o nome do id; sem aspas seria uma variável chamada resultado.

Esquecer de fechar = o resto da linha vira texto. Aspa perdida apareceu no teu <title>"Busca-CEP.

;

Ponto-e-vírgula: fim de frase, o "ponto final" de cada instrução.

O JS até perdoa (adivinha onde acaba), mas às vezes adivinha errado. Capricho: sempre.

.

Ponto: ENTRAR DENTRO. document.getElementById = "dentro do documento, a ferramenta getElementById". dados.uf = "dentro do pacote dados, a caixinha uf". cep.length = "do texto cep, o comprimento".

Ponto errado = procurar caixinha onde ela não mora → undefined.

=

UM igual: ATRIBUIR (guardar na caixinha). const x = 5 significa "x recebe 5", NÃO "x é igual a 5".

Confundir com comparação é bug clássico de iniciante.

=== e !==

TRÊS iguais: comparar de verdade ("é exatamente igual?"). Com ! na frente: "é diferente?". Existe == (dois), mas ele compara "com preguiça" (converte tipos escondido) e causa bugs — NUNCA usar. Regra: comparar é sempre === ou !==.

Usar = dentro de um if (atribuir em vez de comparar) faz o if sempre passar. Armadilha famosa.

+

Duas caras: com números, SOMA (2+3=5); com texto, GRUDA ("R$ " + valor). Por isso o Number() antes de somar.

"50"+"10" = "5010". O bug que o Number() vacina.

Átomo

O que é e por que está ali

Sem ele

if

"SE": abre uma decisão. O código seguinte (entre chaves) só roda se a condição for verdadeira.

Sem if, o bloco roda SEMPRE — vira instrução comum.

( ... )

Os parênteses da condição: embrulham a pergunta que o if faz.

if sem parênteses = erro de sintaxe.

cep

A caixinha criada linhas antes (const cep = ...), guardando o texto digitado.

Nome errado/inexistente = ReferenceError no console.

.

Entrar dentro: "do texto cep, me dá..."

cep length sem ponto = erro de sintaxe.

length

"...o comprimento": quantos caracteres tem. "95980000".length é 8.

Sem .length você compararia o TEXTO com 8, nunca igual → sempre "inválido".

!==

"é diferente de" (comparação de verdade, sem conversão escondida).

Com === a lógica INVERTE: barraria os CEPs certos e deixaria passar os errados.

8

O número mágico da regra: CEP tem 8 dígitos.

Outro número = regra errada; sem ele, a comparação fica manca (erro de sintaxe).

{

Abre o bloco do castigo: o que fazer QUANDO a condição for verdadeira (avisar + return).

Sem chaves, só a linha seguinte pertence ao if — as outras rodam sempre. Fonte clássica de bug.

Lida em voz alta: "SE o comprimento do texto cep for diferente de 8, faça o que está no bloco."

Linha 2 — a leitura: const valor = Number(document.getElementById("valor").value);

Átomo

O que é e por que está ali

Sem ele

Cria uma caixinha nova de valor fixo. É a palavra que DECLARA a variável.

valor

O NOME da caixinha — escolhido por você. Nome bom = frase que faz sentido.

dodument foi teu outro bug — o console gritou "is not defined".

.value

Do elemento achado, o que o usuário digitou. Vem SEMPRE como texto.

Átomo

O que é e por que está ali

Sem ele

await

ESPERE a resposta chegar antes de seguir pra próxima linha.

fetch( )

Semana 3 — API: teu código conversando com o mundo (09/08)

API é o balcão de atendimento de um sistema: você faz o pedido num formato combinado e ele devolve DADOS (não páginas). O Busca-CEP pergunta um CEP ao ViaCEP e mostra o endereço. Tudo que o teu negócio vai vender é costura de APIs: WhatsApp, Tray, ERP.

Peça

Tradução / o que faz

Detalhe que salva

fetch("url")

fetch = buscar: vai até o endereço da internet e traz a resposta.

A URL se monta com o + grudador: "...ws/" + cep + "/json/".

await

esperar: para ali até a resposta chegar.

Internet demora. Sem await, o código segue de mãos vazias.

async function

assíncrona: aviso na testa da função de que ela espera coisas.

Regra de par: usou await dentro, precisa de async na frente.

resposta.json()

Traduz a resposta pro formato de dados.

Também leva await. Se a resposta NÃO for JSON (erro 400), essa linha EXPLODE — olha o console.

JSON

JavaScript Object Notation: o idioma universal dos sistemas.

Chave e valor, "cidade": "Anta Gorda" — caixinhas empacotadas pra viajar.

dados.chave (o PONTO)

Entra DENTRO do objeto: dados.localidade pega a caixinha localidade do pacote.

Teu primeiro OBJETO — a estrutura que vai carregar clientes no mini-CRM.

.length

comprimento: quantos caracteres tem o texto.

cep.length !== 8 barra CEP quebrado ANTES de gastar internet.

!==

diferente de.

O irmão contrário do igual.

undefined

indefinido: pediu uma caixinha que não existe no pacote.

"undefined undefined" na tela = leu campos de um pacote de erro.

Lições da semana 3 (pagas com bug)

  • CHAVE DE API SE COPIA, NUNCA SE DIGITA DE MEMÓRIA: escreveu dados.error (inglês) mas o ViaCEP responde "erro" (português). O nome é o que o servidor diz, letra por letra. Vale pra ViaCEP, Tray, WhatsApp, tudo.
  • As DUAS guardas do formulário com API: formato ANTES do fetch (não viaja com dado quebrado) · existência DEPOIS do fetch (pacote de erro não tem endereço dentro). Esteira: lê → guarda → viaja → guarda → mostra.

Semana 4, parte 1 — SQL: a língua de perguntar a dados (09/08)

Banco de dados = arquivo especializado em guardar informação organizada em TABELAS (planilha blindada: colunas com nome e tipo, linhas com dados). SQLite = o banco mais usado do planeta, mora num arquivo simples (clientes.db). SQL = a língua de conversar com ele. E a novidade arquitetural: o código rodou FORA do navegador — arquivo .js puro, executado pelo Node no terminal (node banco.js).

Peça

Tradução / o que faz

Detalhe que salva

require("node:sqlite")

require = requisitar: "Node, me empresta tua ferramenta de SQLite".

Só existe no Node — navegador não tem.

new DatabaseSync("arquivo.db")

Abre (ou CRIA se não existir) o arquivo do banco.

O arquivo nasce na pasta na primeira rodada.

db.exec("...")

exec = executar uma ordem SQL (criar, inserir, apagar).

Para ordens sem resposta.

db.prepare("...").all()

prepare = deixa a pergunta pronta; .all() = executa e traz TODAS as linhas.

O () vazio é o ato de chamar sem ingredientes.

CREATE TABLE IF NOT EXISTS

CRIE A TABELA SE NÃO EXISTIR — o molde: colunas, tipos.

Roda toda vez sem medo: se existe, pula.

INTEGER · TEXT · PRIMARY KEY

Tipos: número inteiro · texto · chave primária (o id único da linha, preenchido sozinho).

PRIMARY KEY = o CPF da linha.

INSERT INTO t (colunas) VALUES (valores)

INSIRA NA tabela, nestas colunas, estes valores — na MESMA ordem.

Vírgula entre cada coluna E cada valor.

SELECT * FROM clientes

SELECIONE tudo DA tabela. O * = "todas as colunas".

SELECT nome, telefone FROM... traria só essas.

WHERE condição

ONDE: o filtro do SELECT — só as linhas que passam no teste.

É o if do mundo SQL. Sem WHERE, vem todo mundo.

DELETE FROM clientes

APAGUE DA tabela... TUDO, se não tiver WHERE.

⚠️ A frase mais perigosa do SQL. Respeito eterno.

console.log(coisa)

Imprime no terminal — o primo do alert pra programas sem tela.

É como programa de servidor "fala".

node arquivo.js

Manda o Node executar teu arquivo.

Terminal → New Terminal já abre na pasta certa.

As perguntas do Gabriel, respondidas (09/08)

  • POR QUE A DATA É 2026-05-11 (ano-mês-dia)? Porque nesse formato, ordem alfabética = ordem cronológica — dá pra comparar datas com < e > como se fossem palavras. Do pedaço maior (ano) pro menor (dia). É por isso que o mundo inteiro grava data assim em banco.
  • POR QUE A DATA USA ASPAS SIMPLES? Duas línguas aninhadas: o JavaScript embrulha a frase SQL inteira em aspas DUPLAS; dentro do SQL, texto e data usam aspas SIMPLES. Cada língua com a sua — assim uma não briga com a outra.
  • O QUE SÃO OS === EM VOLTA DE "CLIENTES SUMIDOS"? Nada de operador! Estão DENTRO de aspas = são só caracteres desenhando uma moldura no terminal. Fora de aspas, === compara; dentro, é enfeite. Aspas = texto literal, sempre.
  • POR QUE console.log("...") TEM ASPAS E PARÊNTESES? Aspas = "isto é texto a imprimir"; parênteses = a ENTREGA do ingrediente à função. Sem parênteses não há entrega; sem aspas o JS procuraria uma variável com aquele nome.
  • EDITOR MOSTRA; DISCO EXECUTA: o node roda o que está SALVO no arquivo, não o que está na tela. Rodou e não saiu nada? Bolinha ● na aba = esqueceu o Cmd+S. (Arquivo vazio roda "com sucesso" em silêncio.)
  • O VS CODE NÃO FALA SQL: erro dentro das aspas ("TABLEIF", vírgula faltando) passa batido pelo editor — pra ele é só texto. Quem confere é o SQLite NA EXECUÇÃO, gritando no terminal com near "PALAVRA" (perto de onde quebrou). Esteira de sempre: roda, lê, conserta, roda.
  • DADOS SOBREVIVEM: variável morre quando o programa acaba; o arquivo .db FICA. Primeiro código teu com memória permanente. Efeito colateral: INSERTs rodam de novo a cada execução → duplicatas; na fase de testes, DELETE FROM depois do CREATE limpa antes de semear.
  • ESTRUTURA vs DADOS: o CREATE TABLE (molde) é desenhado por humano, uma vez — modelagem. Os INSERTs, na vida real, chegam sozinhos: formulário, API, importação. Os teus 3 à mão são dados-semente (andaime de teste).
